## 二、逐项分析

### E1 · 渲染成功后仍报 WinError 3，整批资产判失败 ⭐ 最高优先级

**取证链（已闭环）**

1. `output/performance/c805e3ba-….json`（木灵根少年）记录 `"success": true`，
   `finished_at 21:29:53`；
2. `F:\…\ComfyUI-2nd\output\comic_drama\测灵根_第一集\character\周野_00001.png`
   等 3 张图**至今仍在** ComfyUI output 里 —— 说明应用**没有消费**产物；
3. 日志里 `[actual_params]` 与 `ERROR` 之间**没有** `[资产质检]` 行 → 异常点在
   `gen_base()` 返回后、质检调用前。

**代码缺陷**（原 `app.py:3891-3894`）

```python
scratch_base = os.path.join(scratch_dir, f"base_try{attempt + 1}.png")
shutil.move(base_files[0], scratch_base)
```

1. 目标目录 `scratch_dir` 是在**循环头部**（渲染前 20~40 秒）建的；渲染期间被外部
   清理/并发任务改动后，move 就会失败；
2. ComfyUI 在 `F:`、项目产物在 `H:` —— **跨盘**。`shutil.move` 必然走
   `copy2` + `unlink` 回退分支，而 `copy2` 里的 `open(dst,'wb')` 正是抛
   `WinError 3`（`ERROR_PATH_NOT_FOUND`）的那一步；
3. 盲取 `base_files[0]`：`get_output_files` 会平铺 history 里**所有**输出条目
   （含临时/预览图），第 0 个未必是正式产物，也可能已被并发执行体取走；
4. 一失败就**整资产判死**，无降级空间 → GPU 白烧、产物留 ComfyUI 无人认领。

**修复**：新增 `app.py::_ingest_comfy_output()`
- 落地前**重新** `os.makedirs(scratch_dir, exist_ok=True)`；
- 只挑**真实存在**的源文件（`os.path.isfile` 过滤）；
- 同盘 `os.replace`（原子）/ 跨盘显式 `copy2 + remove`，**不依赖 `shutil.move`
  的隐式回退**；
- 全不可用时抛出的异常里带**完整源/目标路径与候选清单**，下一次现场可直接定位。

### E2/E3 · 用户暂停被当成资产失败

`app.py` 资产隔离分支是 `except Exception`，`cancellation.Cancelled` 落进去后：

- 记成 **ERROR**（本轮 ERROR 里占 2/5，真故障被淹没）；
- 塞进 `results[i]["error"]` → 前端显示「生成失败」，用户以为资产坏了。

**修复**：新增 `except cancellation.Cancelled` 分支（置于通用 `except` 之前）：
记 info、`stage="已暂停"`、`error=None`、结果带 `"cancelled": True`。

### E4 · fs_atomic 的 `.bak` 快照用的是它自己文档里骂的反模式

`fs_atomic.py` 开头（第 6~16 行）专门论证了「固定临时名 + 并发写者」会把 JSON
写成交错内容，并据此规定活文件必须用「唯一临时名 + fsync + `os.replace`」。
但 `_snapshot_bak` 自己却用 `shutil.copy2(path, path + ".bak")` ——
**固定目标名、非原子的裸复制**。

`.bak` 是**唯一**的损坏恢复来源：两个写者同时快照时，B 以 `"wb"` 截断 `.bak`、
A 还在往里写 → 备份被写坏；此时活文件一旦损坏，`read_json_strict` 的
ValueError 分支只能 fail-loud 抛错，整份数据不可用。

现场印证：`output/autopilot/测灵根_第一集/attempts.json` = `{"1": 0}`，
而 `attempts.json.bak` = `{"1": 2}` —— 活文件与备份**差一整个版本**，
说明 `.bak` 长期停在旧快照（`_snapshot_bak` 每次发布前才更新，中途被
`_clear_dead_letters` 用 `os.remove` 删掉活文件后，`.bak` 成为唯一残留）。

**修复**：`_snapshot_bak` 改用与活文件同一套纪律（唯一临时名 → 写 → fsync →
`os.replace`），并把「校验的字节」与「发布的字节」定为同一份，消除
「校验旧内容、发布新内容」的窗口；抽出的 `_atomic_write_bytes` 同时供
`atomic_write_bytes` 复用。

### E5 · 模型只吐思考内容（2026-10-06 第二轮修复，**代码缺陷，非环境问题**）

**用户质疑点**：日志说「建议降低 reasoning_effort（low）」，但档位**本来就是 low**
（用户原话：「模型的思考等级？现在是 low 啊」）。这条建议确实是废的 —— 顺着它查下去，
发现真正的 bug 在提额判据上。

**根因**（`llm_client.py::chat_json_robust`）

```python
if raised <= cur and _next_tokens(cur) <= cur and self.reasoning_effort:
    downgraded = _downgrade_reasoning_effort()
nxt = max(raised, _next_tokens(...) if downgraded or raised > cur else cur)
nxt = min(nxt, MAX_TOKENS_CEILING)
if nxt <= cur and not downgraded:
    logger.error("…判定为模型/服务端异常…快速失败上浮")
    break
```

`_next_tokens()` 的契约是**恒返回 ≥ 入参**：

```python
def _next_tokens(value):
    for t in ladder:
        if t > value: return min(t, MAX_TOKENS_CEILING)
    return min(value * 2, MAX_TOKENS_CEILING)
```

所以 `_next_tokens(cur) <= cur` **只在 `cur >= MAX_TOKENS_CEILING`(32768) 时成立**。
现场 `max_tokens=19984 / 18184` 时该判据为 False，导致：

- `downgraded` 恒为 False → **降档分支从未被执行**（实际已是 low，本来也无档可降）；
- `nxt` 被算成 `cur` → **额度没用完就 break**，判定「模型/服务端异常」。

即：离 32768 上限还差 12800 token，代码直接宣布「没救了」，而 `max_attempts=3`
还剩 2 次重试预算没用。一个可恢复的额度问题被上报成模型故障 → 整步卡死 →
`pipeline` 判分镜失败。

**更讽刺的是**：模块头部第 104~111 行的实测记录已经写明
`max_tokens 16384 → 只有思考，正文为空` / `24576 → ✅ 成功`，
但 `REASONING_ONLY_TOKEN_FLOOR = 16384` 恰好等于那个**已知会失败**的水位。

**修复**

1. 引入独立判据 `can_raise = cur < MAX_TOKENS_CEILING`，不再拿 `_next_tokens` 的返回值
   当「还有没有空间」的探针；
2. 还能加额度时，**一次跨到上限**（符合模块自己「自救必须一步跨到位，不要 2K
   阶梯小步试探（每步 2~7 分钟）」的结论；且 `max_tokens` 是**上限不是预付**，
   模型提前结束不额外计费，所以直接顶到 32768 是零风险的）；
3. 只有「额度已顶 32768 **且** 档位降无可降」才快速失败上浮
   —— 顺带修掉 `low + 已在上限` 时会空转到耗尽 attempts 的浪费；
4. 失败提示按**实际档位**给建议：已是 low 时不再说「降到 low」，改为提示
   换模型 / 拆小任务 / 稍后重试。

**轨迹核对**（纯算术，无网络/无 GPU/无 IO）

| 档位 | max_tokens | 旧：是否误判没救 | 新：下次额度 |
|---|---|---|---|
| low | 19984 | 是（放弃 12800 额度） | **32768** |
| low | 18184 | 是 | **32768** |
| max | 16384 | 是（而 16384 本身就是空正文水位） | **32768** |
| low | 32768 | 否（空转到耗尽 attempts） | 立即上浮 ✅ |

## 六、第三轮：WinError 3 从「点修复」收敛为「系统性修复」

用户要求「优化好」后复查发现：E1 只修了**资产链路 1 处**，而
`shutil.move(files[0], dst)` 这个反模式在代码库里共 **11 处**，全部具备同样的三个缺陷。
其中 `app.py` 的**分镜主 worker**（`shutil.move(result["files"][0], scratch_png)`）
**一集要跑 20 次**（每镜一次），是风险最高的调用点 —— 也就是说资产链路修好了，
分镜链路照样会以同样方式整集失败。

### 6.1 统一落盘入口 `_ingest_comfy_output()`

签名从 `(files, scratch_dir, dst_name, logger)` 泛化为
`(src_files, dst_path, logger=None, fallback_to_source=False)`，以适配全部 11 处
（它们的目标都是「一个完整路径」，而非「目录 + 文件名」）。新增能力：

- **目标目录幂等创建** —— 不再信任渲染前的 `os.makedirs`；
- **源/目标同路径直接返回** —— 内建了原先散落在调用点的
  `if abspath(src) != abspath(dst)` 守卫；
- **`fallback_to_source=True`** —— 给「搬移只是优化、不是必需」的调用点
  （预演产物），失败时返回仍可用的源路径而不是抛；仍记 warning，绝不静默；
- **异常类型从 `FileNotFoundError` 改为 `RuntimeError`** 并带完整源/目标路径
  —— 跨盘失败的真实原因是 `copy2` 里 `open(dst,'wb')` 的**目标目录**缺失，
  报成 `FileNotFoundError` 会把排查方向误导到「源文件丢了」。

### 6.2 `get_output_files()` 默认只返回磁盘上真实存在的文件

这是更根本的一处：ComfyUI 的 history 是「曾经跑过什么」的记录，它引用的文件
可能已被并发执行体取走、或被 `disk_reclaim` 的输出滚动回收清掉。
原实现原样返回全部条目 → 调用方盲取 `[0]` 拿到不存在的路径。
现在默认过滤（`require_exists=True`），仅「清理类」调用方可退回旧行为。

### 6.4 顺带修掉的两个「我自己引入的隐患」

- `te_3d_render._te_man_js_dir()` 原先是「第一个存在的目录就返回」。若某处存在同名
  但残缺的 `TE_MAN/web/js`（插件装了一半），会一路返回它，随后因「渲染资产缺失」
  直接 return None —— **兜底扫描 `_find_asset_src()` 根本没机会跑**。

### W1/W2 · ComfyUI 空响应被当成 JSON 解析失败

ComfyUI 的 `POST /interrupt`、`POST /history {"clear":true}`、
`POST /queue {"delete":[…]}` 成功时返回 **200 + 空 body**（不是 `{}`）。
原 `_post()` 无条件 `resp.json()` → `JSONDecodeError: Expecting value: line 1 column 1`
→ **每一次打断远端任务、每一次清历史都被记成失败**。这两条是本项目日志里最高频的
WARNING，把真故障淹没了。

**修复**：`_post()` 改为
- 200 + 空/纯空白 body → 返回 `{}`（成功）；
- 200 + 可解析 → 返回结果；
- 200 + 非空但确实是坏 JSON → 仍抛（不掩盖真异常），消息带前 200 字符；
- 非 2xx → 仍抛 RuntimeError。

顺带清掉 `interrupt()` 里两分支重复 `self._post("/interrupt")` 的死代码。

### W3 · VoiceBank 重试风暴

`_auto_fill_voice_bank()` 按角色循环，每个角色提交一次 ComfyUI TTS。
当 ComfyUI 侧 `qwen_tts` 包 import 失败时，**每个角色都报同一条**
`Model class is not loaded`（单条就带 ~2KB traceback）。20 个角色 =
20 次必失败的 GPU 队列提交 + 20×2KB 刷屏。

**修复**：新增熔断 —— 首次命中「模型类未加载」类特征后，本轮剩余角色全部跳过，
只记一条汇总（参考音色本就是可选项，fail-open 与既有口径一致），
并给出修复指引（ComfyUI 侧修 `qwen_tts` 依赖后重启）。

### W4 · TRT 自检日志污染

`trt_engine_check._error_text()` 原为 `json.dumps(messages)`，而一条
`execution_error` 事件带 `traceback` 数组（元素本身是多行字符串）→ 单条
WARNING 数千字符。这坨内容还被写进 `output/trt_engine_status.json` 的
`reason`，于是**每次启动都原样重打一遍**（现场同一段 JSON 出现 3 次）。

**修复**：
- `_error_text()` 改为**提取** `exception_type` / `exception_message` /
  `node_type` / `node_id`（真正的诊断价值所在，如
  `TensorRT library not found!`），不再序列化整个 messages 数组；
- 新增 `_reason_for_log()`：进日志前压成单行、限长 300 字符，超长时提示
  全文见 `trt_engine_status.json`。
