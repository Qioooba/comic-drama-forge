# ADR-0006：交付包需 SHA-256 校验 + 人工批准

- 状态：**已采纳**（2026-10-07 实施）
- 决策者：项目维护者
- 相关：`app/domain/delivery.py`、`app/infrastructure/delivery_repo.py`、`app/api/delivery.py`

## 背景

本项目此前的「交付」只有产物生成（`app/nle_export.py`：SRT / 剪映 draft / FCPXML /
帧清单），**没有交付语义**：

- 不知道交付的是哪一档画幅；
- 不知道交付包由哪些文件构成；
- **不知道这些文件有没有被改过**。

于是交付方拿到的是「导出目录的拷贝」，无法判断它是不是最新的一次导出。
更糟的是：机器跑完就算「完成」——这直接违反协调书 §4「采用 ≠ 批准」：
**机器检查通过永远不等于人工批准。**

## 决策

四件东西一起上：交付预设 → 文件清单 + 每文件 SHA-256 → 机器校验 → 人工批准闸门。

状态机：

```
built ──(机器校验通过)──> verified ──(人工批准且哈希匹配)──> approved
  │                          │                                │
  └── 文件缺失/哈希漂移 ──────┴── 内容变化后批准自动失效 ──> approval_invalidated
```

**「机器校验通过」只把状态推到 `verified`，永远不会推到 `approved`。**
`approver` 为空的批准请求一律拒绝（`DLV-APPROVER-REQUIRED`）。
`system:` / `bot` / `auto` 之类机器账号不构成人工授权。

### 关键决策：批准必须绑**磁盘现状重算**的哈希，而不是清单基线

这是本决策里唯一有真正技术含量的地方，也是最容易被写错的地方。

**清单基线**（build 那一刻记录的 SHA-256）回答的是「*我们以为交付了什么*」。
**磁盘现状**回答的是「*现在磁盘上是什么*」。

交付方拿到的是磁盘上的文件。如果批准绑清单基线，那么：

> 有人在 build 之后改了导出目录里的一个 SRT → 清单没变 → 哈希匹配 → 系统显示
> 「已批准」→ 交付方收到的是**被改过的**文件，而系统说一切正常。

这就是「批准过 A，交付了 B」，而且**系统还主动确认了它**。清单基线把快照当成了保证。

因此：`refresh_disk_state()` 按**磁盘现状**重算 `current_package_hash` / `disk_ok`，
并且在 `get_package()` / `list_packages()` / `save_package()` **三条读路径上都被调用**
（`delivery_repo.py:288`、`:326`、`:332` 的注释写明了这一点）。含义是：

- 批准有效性**永远**按此刻的磁盘算，不依赖任何后台撤销任务；
- 失效不需要「谁去撤销它」——内容一变，下次读到就是失效的。

哈希摘要本身也有性能顾虑：`get_package` / `list_packages` 每次都全量重算，
交付目录里多是 SRT / JSON / XML 文本产物，但**万一是视频不能每次全读一遍**。
所以有 `_SHA_CACHE`，键 = `(绝对路径, 大小, mtime_ns)`。文件一改键就变、缓存自动失效，
不会出现「用旧摘要判成没改」。

### 附带决策：交付元数据目录刻意**不**放进导出目录

`DELIVERY_HOME = output/delivery/`，与 `EXPORT_DIR` 平级。因为交付清单里含文件自身的
SHA-256——如果把清单写进导出目录，清单就会「包含自己的哈希」，形成循环引用。
元数据与被校验的产物必须彻底分家。

## 为什么不选另一条路

**绑清单基线 + 后台定期巡检。** 听起来更省事（读路径不重算）。但「批准仍然有效」
与「文件没被改」之间会有一段**时间差**，而这段差里交付方完全可以取走文件。
授权门禁不能建立在「巡检来得及跑」之上。

**只要 SHA-256 校验，不要人工批准。** 这是最省事的选择，也是协调书 §4 明确禁止的：
机器校验（`verified`）与人工批准（`approved`）是两个独立动作，永不互相隐式升级。
把「文件没被篡改」当成「内容被认可」是范畴错误——前者防篡改，后者是创作判断。

**只记批准时间戳，不绑哈希。** 等于没有门禁。批准之后重新导出一版，时间戳依然
「有效」，于是「批准的到底是哪一版」永远答不出来。

**mtime 作为判据。** mtime 会被 `touch`、会被复制覆盖保留、精度受文件系统限制。
交付门禁不能用它。

## 后果

**正面**

- 交付包内容变则批准**自动失效**，无需后台任务；
- 「批准的到底是哪一版」可追溯（`package_hash` + `approver` + `note`）；
- 状态四态分离：`built` / `verified` / `approved` / `approval_invalidated`，
  与 ADR-0002 的「采用 ≠ 批准」在交付侧闭合；
- 错误码稳定（`DLV-*`），前端按码分支不解析文案。

**负面 / 代价**

- **批准需要额外的显式动作（多一步操作）** —— 这是**有意的摩擦**，用摩擦换误交付。
- 每次读交付包都要按磁盘现状重算摘要（已用 mtime+size 缓存缓解，但不是零成本）。
- `revoke_approval` 是人工动作，**优先于**哈希判定：内容变化不应复活一个已被显式
  撤销的批准。这条容易写反。

**遗留**

- 未做签名（签名 / 时间戳权威）。哈希只能证明「没变」，不能证明「谁在什么时候批准」。
  当前靠 `approver` 字段 + 本地库，对单机工作台够用。
