# ADR-0007：授权门禁 fail-closed —— 模型 / 素材 / 品牌登记

- 状态：**已采纳**（2026-10-07 实施）
- 决策者：项目维护者
- 相关：`config/model-licensing.json`、`app/domain/licensing.py`、`app/infrastructure/licensing_repo.py`、`app/api/licensing.py`

## 背景

改造前 `grep license` = **0 命中**。项目用着若干第三方模型与音乐/素材，
却没有任何地方记录「这东西能不能商用、要不要署名」。

这不是「功能缺失」，是**风险敞口**：

- `FLUX.1-dev` 是**非商用权重**，只有 schnell可商用。项目里两个都装了；
- 现役视频主模型 `minimax-h3`（ref2va 单采模板）的官网 LICENSE 商用条款**至今未核实**；
- 可选超分 DiT `flashvsr-v1.1` 仅研究用；
- 音乐库、素材、品牌与水印版本完全没有登记。

这些模型**已经装在用户的机器上、已经被默认流程调用**。缺的不是「以后加个登记界面」，
是「交付前把住那一道门」。

## 决策

`config/model-licensing.json` 是模型 / 素材 / 品牌的**唯一登记处**。
`app/domain/licensing.py` 是纯领域判定（不 import flask），交付包构建前必须过门禁。

### 铁律：fail-closed —— 未登记即拦住

| 情形 | 判定 | 错误码 |
|---|---|---|
| 模型不在登记表 | 拦住 | `LIC-MODEL-UNREGISTERED` |
| 许可禁止商用 | 拦住 | `LIC-MODEL-NONCOMMERCIAL` / `LIC-ASSET-NONCOMMERCIAL` |
| 授权待核实（`verified:false`） | 拦住 | `LIC-LICENSE-UNVERIFIED` |
| 要求署名但未提供署名文本 | 拦住 | `LIC-ATTRIBUTION-MISSING` |
| 音乐/素材未登记 | 拦住 | `LIC-UNREGISTERED-ASSET` |
| 品牌与水印版本不存在或未启用 | 拦住 | `LIC-BRAND-UNRESOLVED` |
| **登记表读不出来 / 格式非法** | **按最严口径阻断** | `LIC-REGISTRY-MISSING` |

最后一条是 fail-closed 的**核心**：读不到授权信息，**不能等价于**「没有限制」。
登记表读不出来时，正确的默认是「拦住」，不是「放行」——因为登记表读不出来通常
意味着文件损坏、路径错误或部署不全，这些都是配置错误，不是「无授权要求」。

### 关键决策：`minimax-h3` 宁可 `verified:false` 也不猜

登记表现状（`config/model-licensing.json:71-80`）：

```json
{
  "name": "minimax-h3",
  "source": "MiniMax",
  "license_type": "unknown",
  "commercial_use": false,
  "verified": false,
  "attribution_required": true,
  "attribution_text": "",
  "notes": "待核实：现役视频主模型（ref2va 单采模板）。需确认官网 LICENSE 的商用条款后再把 verified 改 true。"
}
```

这是一个**现役、默认被调用**的视频主模型。把它登记成 `verified:false` 意味着
**任何商业交付都会被 `LIC-LICENSE-UNVERIFIED` 拦下**。

这是**有意的**，理由有三：

1. **「不知道」必须可表达。** 授权状态有三种：可商用 / 禁商用 / **不知道**。
   把第三种塞进前两种里，就必然要猜。猜错的方向有两种，而**「猜可以商用」会把
   法律责任转嫁给用户**——用户交了片才发现模型不能用，损失已经发生。
2. **门禁的价值来自「它真的会拦住」。** 如果登记错一行就能放行，门禁就是装饰。
   `minimax-h3` 是最容易触发的那一项（它是主模型），让它真的被拦，门禁才可信。
3. **修复成本极低。** 有人去查 MiniMax 官网 LICENSE，改一个字段即可。
   猜错的修复成本是不可逆的。

`flashvsr-v1.1` 同理。

登记表读侧有 mtime + size 缓存（`_CACHE`），改 JSON 后自动重载，不需要重启服务。

## 为什么不选另一条路

**白名单放行 / 「已知的先放行」。** 需要维护一张「已知安全」清单，
而判断「已知」的依据恰恰是授权信息——循环依赖，且漏一条就是合规事故。

**默认允许 + 事后审计。** 事后审计的前提是已经交付出去了。交付不可撤回。

**在 UI 上给个「我确认授权没问题」的勾选框。** 那把合规责任从系统转给了用户，
而用户往往并不知道模型许可条款。**门禁的价值恰恰在于「不问用户」也能拦住。**

**按模型名硬编码规则。** 许可条款会变，且同名模型不同版本条款可能不同。
规则必须可编辑、可审计，所以落在数据文件里。

## 后果

**正面**

- 商业交付前，非商用模型 / 未核实模型 / 未登记素材**一律进不去**；
- 授权状态是**可审计的数据**（谁、什么版本、什么条款），不是散落在代码里的 if；
- 门禁判定留痕（`licensing_audit.db` 的 `licensing_gate_log`），事后可查；
- 登记表改一行即可放行，**不需要改代码**。

**负面 / 代价**

- **现役主模型默认进不了商业交付。** 这是**真实的功能倒退**，不是理论风险。
  必须有人去核实 MiniMax 的 LICENSE 并更新登记表。在此之前，商业交付只能换模型
  或等核实。这是**有意承担的摩擦**。
- 登记表需要人工维护，且**会过期**（许可条款变更）。本轮无自动抓取。
- 登记表缺失时全量阻断——**部署不全 = 一件也交付不了**。这是有意的，但第一次遇到
  会很意外。

## 关联决策

- ADR-0006 交付包 SHA-256 与人工批准（授权门禁是交付包构建的**前置**，不是后置）
- ADR-0002 采用 ≠ 批准（`verified` 是机器校验，`approved` 是人工批准，二者不合并）
